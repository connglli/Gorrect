# Stage 14 execution semantics proposal

Status: proposal for review, not an accepted contract or implemented feature. [Stage 14](../implementations/2026-10-29-implementation-plan.md#14-add-scalar-control-frames-and-exception-semantics) follows the unfinished [stage 13 composition work](../implementations/2026-10-30-stage13.md). This note proposes the smallest scalar, frame, and completion basis.

## Scope and prerequisites

Keep GIR and artifact formats at version 1. Generate direct Java arithmetic, array access, method invocation, return, and try/catch/finally. Do not add Java expression syntax, mutable scalar variables, arbitrary jumps, virtual dispatch, closures, a generated bytecode interpreter, or a second general-purpose language. Literal `repeat` remains the looping primitive; recursion supplies another bounded call path.

Stage 13b's conditional caller checkpoints are the starting snapshot, not all of stage 13. Its main-thread marker determines an actual checkpoint's site and visit; `HistoryPlan` reserves storage and lexical declarations without predicting execution. Coordinated worker capture and natural conditional/reference-history liveness remain unfinished. Stage 14 must retain those capability gates until their respective prerequisites and frame extensions are independently checked.

Keep dynamically sized/typed arrays, `System.arraycopy`, clone, and copied diagnostic identity in stage 18. Partial arraycopy effects do not belong in the stage 14 operation set. Keep expected heap exhaustion in stage 23, monitor/JIT transition controls in stage 19, and weaker memory modes in stage 20. Real Java calls do not establish physical non-inlined frames or continuous compiled execution without separate VM evidence.

## Current interfaces that constrain the change

| Boundary | Existing mechanism | Required extension |
| --- | --- | --- |
| Frontend | `Operand` has names, long literals, and null; `Instruction` and `Location` use literal slot indices; `GirProgram.instructions()` visits syntax once. | Explicit numeric types, structured scalar branches, method signatures, call/return, and try/catch/finally; structural traversal visits every method definition once and never follows calls recursively. |
| Validation | `GirValidator.Binding` uses shape-or-null for reference/scalar, checks all blocks, reserves released names, and isolates workers. | Distinguish int/long/reference types, validate signatures before bodies, check normal/abrupt flow, and retain invalid-precondition checks before execution effects. |
| Model | `Value.Scalar` stores long; `GraphMachine` stores lexical scopes and bindings with declaring instruction IDs. `Graph.handles()` is keyed by integer declaration alone. | Typed numeric locals and activation-aware handles, frame contexts, pending completion, and explicit normal/exceptional transitions. Graph payload slots remain long. |
| Oracles | `Oracle` and `HistoryOracle` recursively traverse blocks; `ConcurrentHistory` uses explicit tasks and copied thread contexts. `memory()` predicts one concrete access. | Resumable call/unwind tasks, completion in state keys, and outcome-specific accesses, without using engine exceptions as modeled Java throws. |
| Capacity and visits | `HistoryPlan` assumes conditional bodies execute; `CheckpointPlan` maps a site to one lexical declaration set. | Bounded call/branch/handler/finally quotas and actual frame sets per executed capture. A recursive checkpoint's caller declarations vary with its active stack. |
| Emission/runtime | `JavaEmitter` emits `execute` and worker methods; lexical block cleanup emits fences/nulling only on fallthrough. Recorders hold primitive data. | Direct generated methods, dynamic worker context, primitive call/control evidence, and cleanup on return and exceptional exits. No workload-reference frame registry. |
| Observation | `BindingEvidence`, `RunVerifier`, and `SnapshotProjector` accept only worker 0, activation 1. Projection accepts one `execute` frame. Layouts identify methods, variable names, and descriptors. | A capture can cover several frames with unique activation correspondence. Physical root matches include thread, method, depth, BCI, slot, and compiler scope; missing/ambiguous matches remain inconclusive. |

The change crosses these boundaries together. Adding generated helpers while retaining declaration-only handles would merge recursive locals and could incorrectly protect referents or report binding coverage.

## Numeric and branch basis

Recommend two numeric local types: signed Java `int` and `long`. Existing signed literals, data reads/exchanges, CAS results, `same-object`, and reference-state predicates remain long. Predicates remain long 0/1 so existing CAS results control a branch directly; a separate boolean value type is unnecessary for this stage. Reference types remain exact GIR shapes and may hold null.

Proposed statement spellings below are design examples, not syntax accepted by the current parser:

```text
scalar index int 0;
calc next int add index 1;
convert widened long next;
compare smaller int lt index next;
if-scalar smaller {
  write-data node 0 widened;
} else {
  write-data node 0 0;
}
```

`scalar destination type operand` copies a value or binds a literal. `calc destination type operator operands` accepts `add`, `sub`, `mul`, `neg`, and later `div`/`rem` with their declared arity. `compare destination operand-type relation left right` accepts `eq`, `ne`, `lt`, and `le`, producing long 0/1. Greater comparisons use swapped operands. Bit operations, shifts, floating point, boxing, and mixed primitive heap layouts wait for a concrete workload requirement.

Named numeric operands must match the specified type; there is no implicit widening or mixed-type arithmetic. Literals use the instruction's operand type and must fit it. Old instruction literals retain their long interpretation. `convert` explicitly sign-extends int to long or keeps the low 32 bits of long as a signed int. Arithmetic wraps modulo the result width. Comparison uses signed values directly, never subtraction. These rules follow Java's [numeric conversions](https://docs.oracle.com/javase/specs/jls/se17/html/jls-5.html#jls-5.1.3) and [integer operators](https://docs.oracle.com/javase/specs/jls/se17/html/jls-15.html#jls-15.17).

`if-scalar` accepts either numeric type, evaluates the existing value once, records 0/1 for zero/nonzero, and enters exactly one fresh child scope. Negative values are true. Both arms receive static validation even when a constant predicts the choice. Arms do not export declarations or alter outer bindings' release state; explicit release remains restricted to a binding's declaring scope. Outer heap/root writes persist. No scalar assignment or merge instruction is needed: an outer continuation can read an explicitly written data slot, or a method can return a scalar.

## Invalid GIR and modeled Java completion

Use three semantic completions: `Normal`, `Return(value-or-void)`, and `Throw(kind, origin)`. A block stops at its first abrupt completion and releases the scopes it exits. A rejected GIR operation and an exhausted checking budget are engine failures outside this completion set; GIR catch/finally cannot turn them into a valid execution.

Keep all existing instruction preconditions, including null owners, literal bounds, exact shape assertions, and reference-kind restrictions, as invalid GIR. Do not silently make an old null-owner workload into an accepted Java exception test. Introduce explicitly faulting operations for division/remainder and array access/length. Their contracts name both outcomes. A later explicit faulting field access can be added if a workload needs it; static field indices remain literal.

| Operation | Normal post-state and access | Modeled exceptional post-state and access |
| --- | --- | --- |
| Int/long divide or remainder | Bind the numeric result; no shared-memory access. Division truncates toward zero. Minimum value divided by -1 yields minimum value; the corresponding remainder is zero. | Zero divisor throws `ArithmeticException`; no result binding or heap effect. |
| Array length | Bind int length from a non-null array; no mutable element access. Length still comes from the declared fixed shape in this stage. | Null array throws `NullPointerException`; no result. |
| Strong-reference/long array element read | Resolve an int index and read exactly that element; bind a reference/long result. Preserve exact result-shape assertions as invalid GIR. | Null throws `NullPointerException`; otherwise negative or out-of-range index throws `ArrayIndexOutOfBoundsException`. No element read, result binding, or identity increment. |
| Strong-reference/long array element write | Resolve operands and write exactly one element. | The same null-then-bounds checks throw without an element write. `Object[]` accepts any GIR reference; `ArrayStoreException` is not a possible stage 14 outcome. |
| Array CAS/exchange/volatile access, in its follow-up slice | Use the current memory mode and concrete element footprint, including a failed CAS read. | Faults precede the element access and have no atomic event. Validate actual emitted VarHandle exception behavior before enabling a variant. |

Operands are existing values or literals, so operand evaluation itself has no heap effect. Index conversion is always an explicit prior `convert`; Java's narrowing behavior cannot become an undocumented bounds policy. Computed indices apply only to arrays. Do not lower a computed object-field number through a Java switch and claim array semantics. Array null/bounds ordering follows [Java array access](https://docs.oracle.com/javase/specs/jls/se17/html/jls-15.html#jls-15.10.4).

An accepted normal or throw transition consumes its operation step and records its outcome. A modeled throw leaves the failing operation's heap unchanged but does not undo earlier completed operations, calls, or finally writes. Invalid GIR rejection leaves heap, bindings, allocation/wrapper occurrences, activation counters, trace cursor, memory-access bookkeeping, and operation budgets unchanged. Compute the next transition and check its resource needs before committing it. This is a small operation-local preparation step, not a whole-block rollback system.

## Methods and activation identity

Use named static GIR methods with explicit int/long/reference/void signatures. No overloading, captured caller locals, arbitrary Java calls, receiver dispatch, or recursion-specific instruction is necessary. A proposed form is `method descend (ref N node, int depth) returns ref N { ... }`, with `call result descend (node, depth);` and `return operand;`. Void calls omit a result. Parameters are fresh bindings in the callee's own outer scope; source names may repeat in different methods. Reference arguments copy a strong alias, including null. Result shape/type checks happen before the caller result binding is installed.

Return is valid only inside a GIR method; program and worker bodies still reach their structured end. Void fallthrough is an implicit void return. A nonvoid body must structurally exclude normal fallthrough, with every explicit return matching its signature. Use a small completion-set analysis over branches, blocks, handlers, and finally; treat a repeat as potentially completing normally even when its count is positive. Reject source statements after an unconditionally abrupt statement, and validate unused paths without executing scalar arithmetic during static validation. This avoids needing Java's complete definite-assignment or reachability analysis.

Collect method signatures first, then validate every body, including uncalled methods. Keep source instruction/site IDs stable for old files and globally unique across new definitions and the program. Parameter and emitter-required synthetic reference declarations need stable IDs distinct from allocation sites; reserve IDs after all source instruction IDs rather than reusing a call's ID for several parameters. Labels remain globally unique. Method bodies cannot start workers, contain barriers, or bypass worker synchronization through a hidden call. Calls from workers can run ordinary graph operations and collection controls through the existing worker context.

Define a logical binding key as `(worker, activation, declaration)`. Each logical mutator has a positive monotonically increasing activation counter across all visits; main `execute` is activation 1. A new helper call allocates one activation only after call preconditions and resource checks pass. A worker's initial generated invocation also has its own activation; repeated group visits never reuse it. Loops create fresh lexical instances within an activation but cannot have two active instances of the same declaration there. Recursive invocations have different activations. Keep allocation identity `(worker, site, occurrence)` unchanged; calls do not introduce a new object identity domain.

A frame contains method, activation, parent activation, call/continuation site, local scope stack, and any pending completion. Caller scopes remain suspended and visible only to the oracle's root accounting. Copy all frame, completion, activation-counter, and task state in history forks; include them in equality keys and retained-cell charges. A return evaluates its operand once before finally, keeps that value pending, exits the callee, and installs the caller's result only on normal return. A throw never creates a caller result. Release every exited binding once; scalar copies and method-exit markers do not acquire referents.

Require a finite declared maximum number of active GIR helper frames for a program using calls. The limit excludes engine/runtime wrapper frames. Reaching a call that would exceed this asserted bound is invalid GIR, not a modeled `StackOverflowError`. The all-path audit must prove the bound before launch. Actual target stack overflow remains a runtime failure; the bound is not a portable JVM stack-size guarantee. Total calls and empty calls still consume steps. Recursion therefore cannot bypass the existing work budget even when it changes no graph state.

## Catch, unwind, and finally

Add structured `try { ... } catch arithmetic { ... } catch null-pointer { ... } catch array-bounds { ... } finally { ... }`. A try has catches, finally, or both. Exception kinds denote the three supported Java exception classes; duplicate kinds are invalid. A catch introduces a scope but no reference to the Java Throwable, identity, message, cause, or stack trace. Unsupported exceptions and JVM errors remain execution failures. An explicit arbitrary `throw` instruction is unnecessary: division/array operations provide real fault sites and automatically propagate through calls.

Every modeled catch, starting in 14b, requires a demonstrated workload-operation boundary. An enclosing Java catch must not accept a same-kind exception from recording, checkpoint capture, frame bookkeeping, or other harness code. Protect only the direct faulting workload expression where possible; if generated Java control regions also enclose harness calls, their catch dispatch needs an independently checked origin guard before entering a GIR handler or recording an accepted throw. Exception class, the last operation ID, and a preceding genuine fault are each insufficient proof of origin. The precise lowering remains a blocking design decision for 14b; direct Java unwind remains the goal.

Unknown or unproven origin bypasses modeled handler dispatch and leaves the run with its runtime or extraction failure and incomplete evidence. A harness failure cannot become an accepted catch path, a replacement finally outcome, or a successful terminal completion. Test the boundary separately for each supported exception class, including harness faults while a genuine workload throw is pending, so stale origin state cannot authorize a later harness exception.

The first matching catch handles a throw from the try body. Throws from its handler are not caught by a sibling catch. A finally body executes once after the try/selected handler on normal, return, and throw paths. Normal completion of finally resumes the pending completion; an abrupt completion replaces it. Nested finally bodies unwind from the innermost exited region outward. A return value is fixed before finally mutates the heap, while the referenced object's contents may change. This follows [Java try/finally completion](https://docs.oracle.com/javase/specs/jls/se17/html/jls-14.html#jls-14.20.2).

Do not emit source cleanup only at lexical fallthrough. Controlled lifetime fences and primitive activation teardown must execute on every corresponding Java exit. Use actual Java try/finally for workload effects and a separate small generated cleanup region for frame bookkeeping. Bookkeeping cannot supply an accepted modeled exception or override workload completion. Runtime I/O/recording failure aborts the run and retains incomplete evidence; the operation-origin boundary must keep it outside GIR catch semantics even when its Java exception class matches a supported kind.

A pending reference return is a strong semantic value through finally. It needs a distinct synthetic declaration in the model and an explicit named Java local for controlled observation; compiler-generated anonymous return spill slots are not a mapping contract. Multiple pending returns through nested finally need distinct active records. On replacement, drop the superseded semantic obligation even if Java retains an extra physical reference. If a physical frame or named temporary cannot be mapped, the affected capture is inconclusive. Do not omit that root to obtain a pass.

Recommend default expected terminal completion `Normal`; all modeled faults must be caught for the first exception slice, after its origin boundary is demonstrated. A subsequent small slice can permit an explicit single terminal `Throw(kind)` expectation after recording complete unwind and a final capture with all GIR frames released. It must finish through the success/evidence protocol and be verified as an outcome, rather than reinterpret `session.fail` or an incomplete failure prefix as success. A wrong observed outcome with complete attributable evidence is a violation; unrecognized failures retain runtime/extraction classification. Reuse the established operation-origin boundary and prove its terminal-dispatch behavior; optional terminal throws do not defer the origin requirement for caught faults.

## Evidence and local capture

Extend primitive event kinds for arithmetic/conversion results where needed, scalar branch choices, call entry/exit, return, throw origin/kind, handler entry, and finally entry/exit. Keep per-worker order and existing group/round/phase identities; do not introduce a global recorder lock. A call-entry event carries the fresh activation; the call site identifies method and parent through the independently checked stack. Activation/control events suffice to derive current activation for ordinary events without adding it to every event envelope. A normal-operation event and its result/outcome evidence must never disagree about which operation completed.

The recorder contains no workload objects. On direct call edges, controlled emission can save the caller's immutable binding presence and park site as primitive frame records; callee records extend that chain and pop on unwind. Frames record method, activation, parent, worker/thread, and per-declaration presence. This does not replace physical root evidence. A capture's manifest must enumerate every required parked worker and active frame, including a pending return, and reject duplicate/missing activations. Reuse stage 13's coordinated-capture grouping when it is specified; do not create a competing worker rendezvous.

For compatibility, retain reading the single-frame version 1 evidence already produced. Add a separate version 1 multi-frame manifest/envelope if the existing single-frame `BindingEvidence` cannot represent the set without ambiguity. Selection must be explicit in retained artifacts; never infer a layout from file length or treat a missing manifest as an empty frame set. Match frame sets to validated actual call/checkpoint paths, not `HistoryPlan`'s maximum stack or a site-only declaration set.

Metadata Provider's isolated prototype can supply retained classfile method names/descriptors, Code length/maxLocals, and LocalVariableTable names/descriptors/slots/half-open BCI ranges, distinguishing absent and empty tables. It cannot identify an activation. Verify the actual runtime method/declaring class/loader and exact unmodified retained class bytes separately before using that metadata; a retained-byte digest alone does not prove loaded-byte provenance. Recursion and inlining reuse method metadata. A raw-root method/slot without thread, actual frame depth/BCI, and a unique correspondence to the primitive activation chain is insufficient. Preserve ambiguity instead of guessing stack depth or treating caller order as physical-frame evidence.

Natural mode needs a separate path-sensitive analysis over activation values, normal/throw successors, call arguments/results, and pending finally completion. Future semantic use does not certify a physical root, and a stale presence read taken at a caller edge does not justify a natural-history clearing restriction. Keep natural call/conditional/exception capture unsupported until the stage 13 natural-history policy and this extension have independent models. Named-root execution and scalar traces can still exercise calls while live-binding graph obligations report their coverage limit.

## Scheduling, budgets, and statuses

Preserve the all-schedules validity/race audit before both launch and offline trace matching. A successful recorded CAS path cannot excuse an invalid computed index, shape assertion, excess recursion, missing barrier, or ordinary race on another legal path. Arithmetic follows each state's actual values; branches are not nondeterministic guesses. Reference-clearing choices remain frontier choices, and all live frame/argument/pending-result handles protect referents under the controlled policy.

Carry normal and throwing access footprints into `PhaseRace`. A failed bounds check touches no mutable array slot; a finally write does. Calls, return, and local arithmetic add no memory synchronization. Preserve a throwing worker's prior accesses. Initially require workers to catch modeled throws before returning to their direct barrier sequence; do not give an uncaught worker exception the runtime cancellation policy as a portable GIR scheduling meaning. Supporting exceptional worker termination would require a separate join/cancellation contract and all-path proof.

Reserve bounded storage for both branch arms, every catch possibility, finally paths, and all call depths. Use saturated arithmetic and abort planning on configured bounds; never overflow a capacity into a small allocation. Conservative sums may overreserve and yield a checking limit. A quota plan is not an executed trace or evidence of legal recursion. Memoize per-method/per-remaining-depth quota summaries only if needed to avoid repeated expansion; they contain counts, not expected identities or scalar results.

Charge operation/control steps, total activations, active frames/bindings, continuation/completion cells, fork/key state, checkpoints, and trace/identity evidence against explicit existing or narrowly extended limits. Preflight and offline checking use the same accounting. Limit exhaustion is a checking-limit/inconclusive outcome, not a legal Java throw or proof that other schedules are safe. A missing later capture cannot erase an earlier independently proved violation; partial evidence cannot establish a complete pass. Retain stage 13b's distinction between completed final captures and failure prefixes.

## Test obligations and unresolved choices

Use a separate small arithmetic model based on mathematical integers and explicit width reduction, rather than calling the production evaluator. Cover int/long extrema, narrowing, signed comparisons across overflow boundaries, division signs, zero, and minimum/-1. Exhaustively enumerate small CAS-driven branch/call graphs with an independent scheduler; include an invalid/racy path that the saved successful trace does not take. Compare exact allowed outcomes and access footprints, not just one produced run.

Build a small completion-table model independent of production continuations. Check normal/exceptional effects before and after each catch/finally, handler throw escaping sibling catches, return-value capture before finally mutation, nested replacement, acquired-reference scope exit, and repeated/recursive declaration lifetimes. Snapshot engine state, trace cursors, counters, and footprints around rejected calls/operations and budget failures. A modeled throw must show its successful-prefix effects and one charged outcome.

Inject `ArithmeticException`, `NullPointerException`, and `ArrayIndexOutOfBoundsException` independently from recorder, capture, and frame-bookkeeping paths enclosed by each GIR catch kind. Pair these with genuine direct-operation faults that reach the intended handler. Include injections after a caught workload fault, during exceptional unwind, and while finally holds an earlier pending throw; stale operation or origin evidence must not permit handler acceptance or a pass. Unknown/unproven origin must preserve runtime/extraction failure even when the class and last operation ID match an expected workload fault. These are enabling checks for 14b as well as any terminal-throw extension.

Integration checks must compile generated Java with existing warnings-as-errors and Java 17 target compatibility, inspect direct operators/array/method/exception bytecode, run normal/unwind cases on JDK 17/21 and selected configured VMs, and verify retained bundles offline and by exact-class replay. Missing LVT, absent recursive/inlined origins, changed bytes/loaders, malformed frame manifests, corrupted branch/fault markers, later missing captures, and harness failures must retain their distinct unsupported/inconclusive/error outcomes. Installing or compiling a helper alone does not prove a non-inlined or compiled invocation. No OpenJ9-trunk work is part of this proposal.

Agree on numeric/branch statement spellings before 14a. Demonstrate the workload-operation origin boundary before enabling caught faults in 14b; exception class or last operation ID is insufficient. Before the frame/call slices, agree on capture-manifest ownership and stable parameter/synthetic declaration numbering. Recursive capture additionally needs an explicit helper-depth declaration and configured limit, plus unique activation-to-physical-root correspondence. Before full finally/unwind, agree on warning-free lowering of an unconditionally abrupt finally while preserving Java semantics; conditional abrupt finally and faulting operations can provide initial coverage after the origin guard is established. Expected uncaught exceptions also need the terminal-protocol extension. These later decisions do not block 14a, and none is accepted by this note.
